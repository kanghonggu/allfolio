# AF-102 금리 수집 설계 — 한국(ECOS)

- 작성일: 2026-08-13
- 선행: AF-103(수집 스케줄러) 가동 중, AF-100(ECOS 클라이언트) 완료
- 노션: AF-102 (P1 가시화, 규모 S, 영역 BE·DB, 의존성 "ECOS 인증키 — 환율 백필과 공유")
- 후속: AF-104(시장 화면 금리 탭)

## 목적

시장 화면 금리 탭에 쓸 한국 금리 시계열을 수집한다. 대상 6종 —
기준금리 · 콜금리(익일물) · CD 91일 · 국고채 3년 · 국고채 10년 · 회사채 AA- 3년.

## 이번 범위에서 뺀 것

### 미국(FRED)

노션 명세는 한·미를 한 태스크로 묶었지만 **FRED는 별도 키 발급이 필요하고 그건 사용자 작업이다.**
키가 없으면 코드를 다 쓰고도 라이브 검증을 못 해, "돌 것 같은데 확인은 못 한 코드"가 머지된다.
한국은 ECOS 키가 이미 Render에 등록돼 있어 수집→배포→검증까지 한 번에 닫힌다.

FRED와 한·미 기준금리차는 이 설계의 구조(`market_rate` 테이블 + 소스별 수집 서비스) 위에
그대로 얹히는 후속 태스크로 분리한다. **다만 이번에 소스 추상화(`RateSource` 포트)를 미리 만들지는
않는다** — 구현이 하나뿐인 추상화는 두 번째 구현에서 대체로 안 맞고, 그때 고치는 비용이
지금 만드는 비용보다 싸다.

### 화면용 조회 API

AF-101도 수집까지만 하고 멈췄다. 금리 탭 조회는 지수·환율과 함께 AF-104에서 한 번에 설계한다
(시장 화면은 "네 탭 데이터를 한 번에" 부르는 것이 설계 원칙이라, 탭마다 API를 따로 만들면
그 원칙을 어기는 방향으로 굳는다).

## 데이터 모델

`market_rate` 테이블 하나. 엔티티는 `MarketIndexQuoteEntity` 옆
(`unified-asset/src/main/kotlin/.../infrastructure/entity/`)에 둔다.

| 컬럼 | 타입 | 비고 |
|---|---|---|
| `id` | UUID | PK |
| `rate_code` | varchar(20) | 우리가 정한 canonical 코드 (`BASE_RATE`, `KTB_3Y` …) |
| `quote_date` | date | ECOS가 준 기준일. **조회일자가 아니다** |
| `value` | numeric(9,4) | 연 %. `3.5000` |
| `source` | varchar(20) | `ECOS` |
| `collected_at` | timestamp | 마지막 수집 시각 |

- `UNIQUE (rate_code, quote_date)` — 재수집은 값만 덮는다
- `INDEX (rate_code, quote_date DESC)` — 최신값·기간 조회 양쪽에 듣는다

### 슬롯이 없는 이유

지수는 `(코드, 거래일, 슬롯)`이 키였다. KIS 응답에 기준시각이 없어 장중 값과 종가를
구분할 방법이 스케줄 지점밖에 없었기 때문이다. 금리는 다르다 — **공표 기관이 확정한
하루 한 값**이고, ECOS 응답이 기준일(`TIME`)을 직접 준다. 슬롯을 넣으면 같은 값이
슬롯 수만큼 복제된다.

### 파생값을 저장하지 않는다

bp 변동(전일 대비)과 스프레드(10년−3년)는 저장하지 않고 조회 시 계산한다.
저장된 파생값은 원본이 정정될 때 같이 안 고쳐져 화석이 된다 — 그리고 ECOS는 정정한다.

### 휴일에는 행이 없다

주말·공휴일은 ECOS가 값을 주지 않으므로 행을 만들지 않는다. 직전 값을 복사해 채우면
"그날 실제로 공표된 값"과 구분이 사라진다. 화면에서 마지막 값이 필요하면
조회 쪽이 캐리포워드하고, 그 기준일을 함께 표시한다.

### 마이그레이션

`spring.jpa.hibernate.ddl-auto: none`이므로 DDL은 수동이다.
`docs/superpowers/migrations/2026-08-13-market-rate.sql`에 두고 Neon에 직접 적용한다
(AF-101 `market_index_quote`와 같은 절차).

## 수집 대상은 설정이 정한다

`application.yml`의 `market-rate.series`에 종목별로
`code` / `stat-code` / `item-code` / `cycle`을 적는다. 형태는 `market-index.domestic`과 같다.

**코드를 추정해서 넣지 않는다.** ECOS는 틀린 코드에 오류가 아니라 0건을 돌려주므로,
추정한 코드는 "기간이 비었나 코드가 틀렸나"를 구분할 수 없는 조용한 실패가 된다
(AF-100에서 이미 겪었고, 시장 화면 설계 문서의 미결 사항에도 "추정 금지"로 남아 있다).

**미확인 종목은 빈 코드로 두지 않고 설정에서 아예 뺀다.** 빈 코드를 넣으면 수집 대상 수
(`requested`)에는 잡히고 결과는 실패로 남아 매일 경고가 뜬다. 빼면 대상 수 자체가 줄어
"아직 안 넣은 종목"이라는 사실이 그대로 드러난다.

### 코드는 탐색 엔드포인트로 확인한다

`GET /api/admin/rate/ecos/tables` · `GET /api/admin/rate/ecos/items?stat=<통계표>` — 두 목록 API를 그대로
통과시켜 코드와 이름을 눈으로 확인한다. 어드민 전용.

로컬에는 ECOS 키가 없고 Render·GitHub Secret에만 있어서, 배포된 서버를 통하는 것이
사람이 사이트를 뒤지지 않는 유일한 경로다. 일회성 도구가 아니라 남긴다 — 수집이 0건으로
돌아왔을 때 "코드가 죽었나 기간이 비었나"를 가르는 것이 이 엔드포인트다.

`RateCollectService`는 `EcosApiClient`를 그대로 재사용한다. 응답 형식이 환율과 같기 때문이다.

### 파서를 일반화한다

현재 `EcosResponseParser`는 `rate <= 0`인 행을 건너뛰고(`EcosResponseParser.kt:58`),
반환 타입이 `EcosRate(baseDate, rateKrw)`다. 둘 다 **환율 전용 가정**이다.

- `rate <= 0` 거부: 0원짜리 환율은 없으니 환율에는 맞다. 금리에 그대로 쓰면
  **0.00%로 공표된 날이 통째로 사라진다.** 예외도 안 나고 경고 로그만 남는다
- `rateKrw`: 금리를 담으면 이름이 거짓말이 된다

→ 타입을 `EcosObservation(baseDate, value)`로 중립화하고, **값 검증을 호출자가 넘긴다.**
환율은 `> 0`, 금리는 `|값| ≤ 100`(단위 오인·파싱 사고는 잡되 마이너스 금리는 허용).
이름 변경은 컴파일러가 전수로 잡아준다.

금리 전용 파서를 새로 만드는 대안도 있으나, 응답 형식이 완전히 같아 두 벌로 갈라둘 근거가 약하다.
갈라두면 ECOS 응답 형식이 바뀔 때 한쪽만 고치게 된다.

### 주기(cycle)는 종목마다 다를 수 있다

`EcosApiClient.fetchDailyRates`는 경로에 주기 `D`를 하드코딩한다. 기준금리처럼 변경 시에만
공표되는 계열이 `D`로 안 나올 수 있어, **주기를 파라미터로 뺀다.** 기존 환율 호출부는 `D`를 넘긴다.
어떤 주기가 맞는지는 위 탐색 엔드포인트로 확인한 뒤 설정에 적는다.

## 수집 창 — 매번 최근 2주를 다시 조회한다

일일 수집도 백필도 같은 경로(`from`~`to` 기간 조회 + upsert)를 쓴다. 스케줄 실행은
`to = 오늘`, `from = 오늘 − 14일`로 부른다. 달력 기준 14일이면 연휴가 끼어도 영업일이
최소 5~6일은 들어온다 — 영업일을 세지 않는 이유는 공휴일 달력을 들일 만한 값어치가 없어서다.

하루치만 부르지 않는 이유 셋:

1. ECOS 공표가 하루 이틀 밀리는 계열이 있다 — 어제 없던 값이 오늘 생긴다
2. ECOS는 값을 정정한다 — 재조회가 정정분을 자동으로 흡수한다
3. 잡이 하루 실패해도 다음 날 실행이 메운다 — 재실행 절차가 따로 필요 없다

비용은 하루치를 부를 때와 같다(종목당 호출 1회). 멱등하므로 몇 번을 돌려도 결과가 같다.

### 초기 백필

`POST /api/admin/rate/collect?from=2020-01-01&to=<오늘>` 한 번. ECOS 환율 백필과 기간을 맞춘다
(종목당 약 1,600행). 첫날부터 bp 변동이 나오고, 나중에 금리 차트·분석에 그대로 쓴다.

## 스케줄

평일 KST 18:10 (UTC 09:10) 1회. `collect-index.yml`과 같은 구조의
`collect-rate.yml`을 만든다 — `BACKEND_URL`/`SCHEDULER_TOKEN` 시크릿, 끝 슬래시 제거,
https 강제, 재시도, 요약 출력, 부분 실패 애너테이션.

18:10인 이유: ECOS 일별 계열은 마감 후 공표되고, 국내 지수 CLOSE 수집(15:50)보다 뒤여야
같은 시각에 몰리지 않는다. GitHub cron이 5~30분 밀려도 재조회 창이 흡수하므로
정시성에 기대지 않는다.

## 오류 처리

AF-101 정책을 그대로 따른다.

- **종목 하나가 실패해도 나머지를 진행한다.** 요약
  `{requested, collected, inserted, updated, failed, failures[]}`을 HTTP 200으로 돌려주고,
  워크플로가 `failed > 0`이면 애너테이션을 남긴다. 부분 실패로 잡을 빨갛게 만들지 않는다
  (매일 빨간 잡은 아무도 안 본다)
- **수집 대상이 0건이면 500.** 설정 누락을 초록으로 넘기지 않는다
- **건수를 stdout에도 남긴다.** 잡 요약은 UI를 열어야만 보인다 — AF-101에서 이걸 못 남겨
  대상이 조용히 줄어든 걸 못 잡았다
- ECOS 오류는 기존 `EcosApiException` 경로를 그대로 탄다(인증키 마스킹 포함)

## 테스트

- 파서: 0% 행이 살아남는지 / 마이너스 값이 살아남는지 / 100 초과가 걸러지는지 /
  환율 호출자의 `> 0` 가드는 그대로인지
- 수집 서비스: 종목 하나가 예외를 던져도 나머지가 저장되는지 / 요약 숫자가 맞는지 /
  같은 기간을 두 번 수집하면 `inserted`가 0이고 값이 갱신되는지(멱등성)
- 설정: 대상 0건이면 실패로 끝나는지
- 레포지토리: 유니크 제약이 `(rate_code, quote_date)`로 걸리는지
