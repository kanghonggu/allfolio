# 공시 피드 화면 (S12) — 설계

- 작성일: 2026-08-19
- 라우트: `/unified/disclosures` (NavBar 7번째)
- 선행: `2026-08-18-dart-disclosure-design.md` (백엔드 D1). 그 문서의 6절·7절이 이 화면의 데이터 계약이다.
- 범위: ① 보유종목 공시 피드 + ② 임원·주요주주 소유변동 — 한 화면

## 0. 이 문서가 백엔드도 고친다

**화면을 만들기 전에 `DisclosureFeedService`의 정정공시 묶기를 고친다.** FE가 응답을 충실히 그려도 소스가 별개 사건을 숨기면 화면이 거짓말을 한다. 근거는 1절.

## 1. 선행 수정 — 정정공시 묶기가 별개 사건을 숨긴다

현재 구현은 `(corp_code, report_nm_norm)`으로 묶어 최신 건만 노출하고 나머지를 `supersededCount`로 접는다. **같은 이름의 서로 다른 사건이 함께 접힌다.**

실측(6영업일, `is_material` 3,507행) 기준 묶기 키 비교:

| 묶기 키 | 화면 노출 | 접힘 | 그중 오접기(정정 아님) |
|---|---|---|---|
| **① 현재 구현** `(corp_code, norm)` | 3,264 | 243 | **137** |
| ② `+ flr_nm` | 3,394 | 113 | 9 |
| ③ `+ 정정 있을 때만 접기` | 3,401 | 106 | 0 |
| **④ 둘 다** | **3,403** | 104 | **0** |

### 왜 Tier 4에서 최악인가

`임원·주요주주특정증권등소유상황보고서`는 **임원 각자가** 내는 보고서인데 이름이 전부 같다. 실측:

```
한미약품     23건 → 1건만 노출, 22건 숨김
한미사이언스  16건 → 15건 숨김
카카오뱅크    11건 → 10건 숨김
키스트론       8건 · 드림어스컴퍼니 8건 · NAVER 6건 …
```

접두어 없이 묶이는 그룹 46개 중 **43개가 Tier 4**이고, 거기서만 131행이 숨겨진다. ②섹션의 소스가 되는 바로 그 공시들이다.

비-T4도 있다:

| Tier | 회사 | 정규화된 이름 | 건수 |
|---|---|---|---|
| 1 | 두산퓨얼셀 | `단일판매·공급계약체결` | 4 (별개 계약 4건) |
| 2 | SNT홀딩스 | `현금·현물배당결정(자회사의 주요경영사항)` | 3 |
| 3 | 아이에스동서 | `매매거래정지및정지해제(풍문등조회공시)` | 2 |

### 채택: ④

```
묶기 키   (corp_code, report_nm_norm, flr_nm)
접기 조건  그룹에 is_correction = true 인 행이 하나라도 있을 때만
```

`flr_nm`이 Tier 4의 임원을 가른다(실측상 T4의 `flr_nm`은 사람 이름 — `황상연`·`백가람`). 나머지 Tier는 `flr_nm`이 회사 자신이라 키에 넣어도 결과가 안 바뀐다. 정정 조건이 "같은 이름 별개 사건"을 남긴다.

**오접기가 0이 되고 진짜 정정 104행은 그대로 접힌다.**

> **완벽하지 않다.** 한 회사가 30일 안에 같은 이름으로 정정 하나와 신규 사건 하나를 내면 여전히 함께 접힌다. 실측 표본에서는 0건이었다. 완전한 해결은 원문 XML의 원본 `rcept_no` 참조를 파싱해야 하는데, 백엔드 설계 7절이 "값어치가 없다"고 판단한 그것이다.

## 2. 화면 구조

```
공시                                          최근 30일

┌ 보유종목 공시 ──────────────────────────────────┐
│ [1] 자기주식취득결정                    08-18 ↗ │
│     삼성전자 005930                            │
│ [3] 소송등의제기·신청          정정 2회  08-17 ↗ │
│     SK하이닉스 000660                          │
│ [4] 임원·주요주주특정증권등소유상황보고서  08-17 ↗ │
│     한미약품 128940 · 황상연                    │
│ ──────────────────────────────────────────── │
│ 정기보고서 10건                             ▾  │
└────────────────────────────────────────────┘

┌ 임원·주요주주 소유수량 변동 ─────────────────────┐
│ 삼성전자 005930                                │
│ 박형신 · 비등기임원 상무      761주  −500  08-17↗│
│ 대교 000000                                   │
│ 대교홀딩스 · 10%이상주주  47,971,200주 +1,800,000│
└────────────────────────────────────────────┘
```

### Tier 5는 접는다

정기보고서가 실측 상장사 5,394건 중 **2,846건(53%)**이다. 반기보고서 마감 시즌엔 보유 10종목이면 T5만 10건이고 T1~T4는 0~2건일 수 있다. 평평한 목록이면 화면이 반기보고서 더미로 보인다.

**버리지 않고 접는다** — 백엔드가 `is_material=true`로 저장하고 정렬로만 뒤로 민 것과 같은 판단이다. 실적 발표는 놓치면 안 되는 정보다.

요약 행(`정기보고서 N건 ▾`)을 누르면 펼친다. 펼침 상태는 URL에 두지 않는다 — 탭과 달리 뒤로가기로 돌아올 대상이 아니다.

### Tier 배지는 중립 표기

**숫자와 색만 쓰고 분류명("위험" 등)을 붙이지 않는다.**

백엔드 스펙 8절이 기록한 기지 오분류 때문이다 — `매매거래정지`(T3)가 부정형까지 잡아, 27건 중 `주권매매거래정지해제`(= 정지가 **풀린** 것)가 12건이다. `상장폐지`도 `절차 미진행` 안내를 잡는다.

백엔드에서는 정렬 순위 문제였다. **화면에 "위험" 배지를 붙이는 순간 주장이 된다.** 정지가 풀렸다는 공시에 위험 딱지가 붙는다.

`report_nm` 원문이 이미 사실을 말하므로 분류명을 덧붙일 값이 없다. S13에서 키워드를 고친 뒤 재검토한다.

## 3. 카피 제약 — 지키지 않으면 기능이 위험해진다

백엔드 설계 원칙 3·9절에서 그대로 온다.

**② 섹션에 "매수"·"매도"·"장내매수"를 쓰지 않는다.** `elestock`에 변동사유 필드가 없어(30개사 3,922행 전건 확인) 무상증자·스톡옵션 행사·상속과 장내매수를 구분할 수 없다. 부호와 수량만 낸다:

| 쓸 것 | 쓰지 말 것 |
|---|---|
| 소유수량 변동 | 임원 매수 |
| `−500` · `+1,800,000` | 500주 매도 |
| 지분율 46.07% | 지분 확대 |

**큐레이션 뉘앙스 금지.** "주목 종목", "매수 신호", "관심 종목" 류는 유사투자자문 소지가 있다(9절).

**모든 행에 원문 링크.** `https://dart.fss.or.kr/dsaf001/main.do?rcpNo={rceptNo}` — 요약 생성 대신 링크 제공이 원칙이다.

**지분율 `0.00`은 "변동 없음"이 아니다.** 0.005% 미만이 `NUMERIC(7,2)`에 반올림된 것이다(실측 6행). 수량 필드가 진실을 들고 있다. 이 레포엔 `0`과 `null`을 혼동해 사고 난 전례가 있다.

## 4. 상태 처리

`components/ui/states.tsx` 프리미티브를 재사용한다. **넷을 구분한다** — 문구가 달라야 하기 때문이다.

| 상태 | 조건 | 문구 방향 |
|---|---|---|
| 로딩 | 요청 중 | 기존 `LoadingState` |
| 보유종목 없음 | `items`·`insiderTrades` 둘 다 비고 보유가 0 | 계좌 연결로 유도 — **행동이 필요한 상태** |
| 공시 없음 | 보유는 있으나 기간 내 공시 0 | "최근 30일간 공시가 없습니다" — **정상 상태** |
| 오류 | 요청 실패 | 기존 `ErrorState` + 재시도 |

두 번째와 세 번째를 같은 문구로 처리하면, 계좌를 안 연결한 사용자가 "공시가 없구나"로 오해한다.

> **보유종목 수를 백엔드가 안 준다.** 현재 응답은 `{ items, insiderTrades }`뿐이라 "보유 0"과 "공시 0"을 FE가 구분할 수 없다. **응답에 `heldCount: Int`를 추가한다** — 서비스가 이미 `findHeldStockCodes`로 알고 있는 값이라 추가 쿼리가 없다.

## 5. 조회 구간

**최근 30일 고정.** 기간 선택 컨트롤을 만들지 않는다.

백엔드가 `from` 파라미터를 받지만 v1에서는 노출하지 않는다 — 푸시가 없어 "앱 진입 시 확인"이 사용 패턴이고, 30일은 그 패턴에 맞는 창이다. 선택지를 주는 것은 사용자가 기간을 고민하게 만드는 대가를 치른다.

헤더에 `최근 30일`을 명시해 무엇을 보고 있는지는 분명히 한다. 필요가 확인되면 v2에서 프리셋(7·30·90일)을 붙인다.

## 7. 테스트

**백엔드** — 기존 `DisclosureFeedServiceTest`에 추가:
- 같은 회사·같은 이름인데 **정정이 없으면 접히지 않는다** (두산퓨얼셀 4건 형태)
- 같은 회사·같은 이름인데 **`flr_nm`이 다르면 접히지 않는다** (한미약품 임원 23명 형태)
- 정정이 있으면 접히고 `supersededCount`가 맞다 (기존 테스트 유지)
- `heldCount`가 보유종목 수와 같다

**프런트엔드 — 자동 테스트를 만들지 않는다.**

확인한 사실(2026-08-19): `frontend/allfolio_app`에 테스트 파일이 0개고, `package.json`의 `scripts`는 `dev`·`build`·`start` 셋뿐이며, 테스트 러너 의존성(jest·vitest·testing-library·playwright·cypress)이 하나도 없다.

**이 태스크에서 테스트 인프라를 새로 세우지 않는다.** 러너 도입은 그 자체로 별건이고, 화면 하나를 만들면서 곁다리로 결정할 일이 아니다.

대신 **수동 검증 항목을 구현 계획에 명시한다** — 브라우저에서 확인할 것:

| 확인 | 방법 |
|---|---|
| 보유종목 없음 / 공시 없음 문구가 갈리는가 | 데모 계정과 빈 계정 |
| T5 접기·펼치기 | 반기보고서가 있는 구간으로 조회 |
| 정정 표기 | `supersededCount > 0`인 행 |
| 원문 링크가 실제 DART 문서로 가는가 | 클릭 |
| ②에 매수·매도 표현이 없는가 | 화면 전체 훑기 |
| 다크·라이트, 모바일 폭 | 기존 화면과 같은 기준 |

## 8. 범위 밖

- **기간 선택 컨트롤** — 5절
- **종목별 필터** — 보유 종목이 수십 개가 되면 필요하다. 지금은 실사용 계정이 6종목이다

- **푸시 알림** — 백엔드 설계가 범위에서 제외했다
- **S13 화이트리스트 튜닝** — 별건. 그전까지 Tier 배지를 중립 표기로 두는 것이 이 문서의 대응이다
